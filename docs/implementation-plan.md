## Этап 1: краткий бриф

Для кого: Валерия и все зарегистрированные пользователи, которым она передаст обычную ссылку на приложение. Возможности работы с карточками одинаковые; новые предметы добавляются только по запросу Валерии.

Задача: создавать и учить карточки, быстро добавлять их через Google Sheets, делиться готовыми наборами и свободно изменять взятые личные копии.

Основной сценарий уже согласован: собственная таблица и приложение отражают один личный набор; публикация создаёт отдельную версию; «Взять себе» создаёт независимую копию с именем исходного автора, в том числе в подключённой таблице получателя.

Согласованный макет включает разделы «Учить», «Мои наборы», «Библиотека» и «Профиль» с подключением Google Sheets.

Публикация: в конце, после итоговой проверки. Промежуточная работа — на тестовой версии.

### Решения пользователя

1. Новые предметы определяет только Валерия: она сообщает помощнику название, и он добавляет предмет по её запросу. Одногруппники не могут создавать предметы, но могут создавать темы и карточки. Полный список предметов заранее не требуется. Отдельный административный экран добавления предметов для первого выпуска не запрошен.
   Текущий утверждённый список: «Анатомия», «Латынь», «Микробиология».
2. Валерия передаёт обычную ссылку на приложение; желающие регистрируются и пользуются им. Отдельных приглашений, заявок, кодов группы и ручного одобрения вступления нет. Общая библиотека доступна зарегистрированным пользователям; личные наборы, таблицы и прогресс остаются личными.

3. Удалённая личная карточка исчезает из обучения, но её можно восстановить из «Корзины». Пользователь согласовал возможность восстановления; срок автоматического удаления из корзины не задан, вводить его без отдельного решения не нужно.
4. Если одну личную карточку изменили в приложении и в ещё не обновлённой таблице несовместимыми способами, показываем оба варианта и предлагаем выбрать, какой оставить. Это не касается независимых копий у разных пользователей. Обе возможности согласованы после объяснения на примерах.

## Ограничения, которые переносим из правил разработки

- Сохранить существующие аккаунты, вход, карточки, личные правки, результаты «Знаю / Не знаю / Не уверен» и расписание повторений.
- Новая функция не расширяет доступ к чужим личным карточкам, таблицам и прогрессу. В общей библиотеке зарегистрированным пользователям видны только явно опубликованные материалы.
- Ошибка Google или базы не должна выглядеть как пустой набор и приводить к сохранению пустых данных поверх существующих.
- Повторная отправка, обновление страницы и сортировка строк не должны создавать случайные дубликаты или сбрасывать прогресс.
- Изменения разных пользователей и одновременные правки должны сохраняться по согласованным правилам; нельзя молча перезаписывать всю коллекцию устаревшей копией.
- Интерфейс проверяется в браузере на компьютере и телефоне, с длинными текстами, пустыми состояниями и ошибками.
- Для проверки разных пользователей нужны разные браузерные сессии, а не две вкладки с одной общей cookie входа. Для каждого профиля используется своя таблица.
- Проверять каждый этап отдельно; исправить найденные ошибки и повторить проверку до перехода дальше.
- В отчётах различать локальную проверку, GitHub, развёртывание Vercel и проверку поведения на рабочем сайте. HTTP 200 не заменяет интерактивную проверку.
- Новые ошибки разбирать и фиксировать правило предотвращения в PROJECT_RULES.md.
