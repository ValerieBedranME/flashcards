# Правила проекта

- Перед публикацией на serverless-хостинге проверять запись данных: аккаунты и прогресс должны храниться во внешней постоянной базе, а не в файловой системе функции или /tmp.
- Защищать весь цикл чтения и изменения данных транзакцией между экземплярами приложения: локальный threading.Lock этого не обеспечивает.
- Имя пользователя в URL или localStorage не подтверждает вход. Каждый доступ к личным карточкам и прогрессу проверять по серверной сессии.
- Не сообщать об отправке кода восстановления, если отправка писем отключена.
- В тестах закрывать ответы, отдающие файлы, через контекстный менеджер, чтобы не оставлять открытые файловые дескрипторы.
- Восстановление пароля на Vercel должно использовать доступный серверу почтовый API или SMTP с TLS, а не путь к скрипту на компьютере. Проверять реальную отправку отдельно от успешной сборки сайта.
- Коды восстановления хранить в виде HMAC, ограничивать срок, число попыток и частоту отправки; привязывать к конкретному профилю и версии пароля. Счётчик неверных попыток должен сохраняться даже при HTTP 400.
- Проверять вход по имени и email, а также освобождение кнопки входа при сетевой ошибке. Старые локальные профили не появляются в новой базе автоматически.
- Перед инструкциями по Vercel проверять текущую страницу и перекрывающие окна. Если пользователь не видит кнопку, открыть нужную форму и заполнить несекретные поля самостоятельно, затем передать ввод секрета пользователю.
- Для Gmail удалять разделительные пробелы, включая неразрывные, из скопированного пароля приложения перед SMTP-входом. Для других SMTP-провайдеров не изменять содержимое пароля. При проверке формы с секретом скрывать его значение в выводе инструментов.
- На странице Production различать Save в блоке Branch Tracking и Save в окне Add Environment Variable. Подтверждать сохранение по наличию нужного имени в списке переменных, а не по закрытию окна. Несекретные почтовые настройки сохранять отдельно, чтобы при передаче формы пользователю оставался только пароль.

- Прогресс обучения считать по последней оценке каждой доступной карточки, отдельно от срока повторения. Сумма «Знаю / Не знаю / Не уверен» должна совпадать с числом карточек в работе; неоценённые и удалённые карточки не входят в эти счётчики. Проверять обновление после занятия без перезагрузки.
- В тестах сроков повторения не переносить общее время за срок действия сессии: иначе проверка прогресса превращается в проверку истёкшего входа.
- Названия оценок во всех экранах приложения: «Знаю», «Не знаю», «Не уверен». Не менять род формулировок по полу пользователя.
- Архитектуру FlashCards объяснять пользователю сначала через 3 коротких шага и конкретные действия с карточками. Технические варианты, устройство хранения и подробные сравнения давать только по запросу; длинное объяснение мешает понять основное предложение.
- При реализации Google Sheets и библиотеки следовать `docs/shared-decks-and-google-sheets.md`: равные возможности всех участников; взятый набор появляется и в приложении, и в личной подключённой таблице; исходное авторство сохраняется, а правки копии не меняют оригинал.
- Для этой доработки применять согласованный процесс Billion Game MVP, зафиксированный в `docs/implementation-plan.md`: до кода согласовать недостающие правила, сценарии, макет и проверки; выполнять и проверять этапы последовательно; публиковать в конце. Уже согласованные решения не запрашивать повторно.
- Перед вопросом о техническом поведении давать один короткий бытовой пример: «Корзина» с восстановлением вместо необъяснённого «архива», две правки одной собственной карточки вместо необъяснённого «конфликта версий». Просьба объяснить правило не означает его согласование.
- При правках согласованного макета сохранять заданные пользователем надписи дословно и отражать актуальный список предметов во всех связанных экранах и требованиях. Новый предмет проверять в том числе без тем и карточек.
- Новые Flask endpoints именовать с отдельным префиксом: одинаковые имена функций разных модулей не должны мешать запуску приложения.
- До внешней записи сохранять идентификаторы и задание повтора в постоянной базе. Проверять отдельно потерю ответа и подтверждённый HTTP 503: нужное состояние повтора должно сохраниться; неожиданный HTTP 500 должен откатываться.
- При импорте учитывать изменение новой строки до записи служебных ID и повторное добавление одинакового текста после успешного импорта. Незавершённые строки не давать изучать; совпадение текста не является постоянным ID.
- Новые строки таблицы должны уметь дополнять полученную независимую копию. Если название подходит нескольким личным наборам, не выбирать первый молча.
- Выбор спорной правки привязывать к отпечатку именно увиденных пользователем вариантов, включая сценарии «удаление против изменения» и третью правку до выбора.
- В адаптивной проверке после установки viewport измерять фактический innerWidth проверяемой вкладки: изменение размера выбранной вкладки браузера не доказывает размер другой вкладки.
- Не заявлять полную защиту одновременных правок Sheets по имитационным тестам: прямую запись человека в ту же ячейку между чтением и записью API проверять и проектировать отдельно. Не объявлять интеграцию готовой без реальных таблиц двух пользователей.

- Сетевые запросы Google не должны удерживать общую блокировку базы. После освобождения блокировки никогда не сохранять старый снимок всего документа пользователей: объединять только изменения с заново прочитанным состоянием и проверять конкурирующую запись отдельным потоком. Создание внешнего файла резервировать отдельно до сетевого обращения.
- Изменения русскоязычных документов предпочтительно вносить через apply_patch. Ошибка кодировки вспомогательного скрипта не исправляется успешным запуском следующей команды: проверять каждый результат до фиксации изменений.
- Для синхронизации Google проверять точный снимок перед записью, сохранённый в одном атомарном пакете с самой записью. Повтор узнавать по сохранённому заданию, а не только по совпадению текущего текста: после потерянного ответа человек мог снова отредактировать таблицу.
- При перемещении строк одновременно с записью не угадывать принадлежность данных по новой позиции. Сохранить полные снимки и предложить восстановление в новый файл; предыдущий файл и личный прогресс оставить доступными.
- Интеграционные проверки PostgreSQL выполнять только в явно отдельной базе `flashcards_qa_*`, в собственных временных схемах. Пропущенные проверки без подключения не считать пройденными.
- Перед повторным нажатием Save в настройках внешнего сервиса проверить, что поле уже превратилось в подтверждённую запись, а после Save проверить список: фокус на кнопке не означает сохранение.
- При работе с секретами через браузер не выводить полный AX/DOM после раскрытия значения. Передавать скопированное значение прямо в локальную форму сохранения, проверять только факт сохранения и права файла, затем скрывать значение и очищать использованный буфер.
